### 1.3 三条 numpy 警告

`memory_index.py:74` 的 `sims = self._matrix @ q` 在全量零向量（或 `q` 为零向量）时触发：

```
RuntimeWarning: divide by zero encountered in matmul
RuntimeWarning: overflow encountered in matmul
RuntimeWarning: invalid value encountered in matmul
```

这是矩阵乘法的数值边界问题——当所有事实向量都是零向量（如新库或全事实无效时），归一化后的矩阵乘零向量得到 `0/0`。**这是 numpy 已知行为**，见 [numpy/numpy#28687](https://github.com/numpy/numpy/issues/28687)（macOS M4 上 matmul 除零警告）。代码本身没有逻辑错误，但应增加零向量防护。

### 3.2 网络查证的关键论断

#### 论断 A：Python `exec` 沙箱可绕过

**WorkBuddy 审查 #1** 声称 `_python` 工具的 `exec(compile(...), {"__builtins__": safe})` 不阻止源码中的 `import subprocess`。

**查证结果：✅ 正确**。已知多个 CVE 验证此技术：

- [GHSA-4mr5-g6f9-cfrh](https://github.com/advisories/GHSA-4mr5-g6f9-cfrh) / [CVE-2026-47392](https://vuldb.com/cve/CVE-2026-47392)：通过 `print.__self__` 或 `type.__subclass__` 等途径绕过受限 exec，恢复 `__builtins__` 并逃逸沙箱。
- [cleverthis.com/cleveragents-core/issues/6587](https://git.cleverthis.com/cleveragents/cleveragents-core/issues/6587)：`TransformExecutor` 沙箱暴露 `type` 内置，允许通过元类重构 `__import__`。
- [Langflow 安全文件](https://github.com/langflow-ai/langflow/blob/976ec789/src/lfx/src/lfx/utils/python_repl_security.py)：主流 Agent 框架对此采取了专门防御（禁用 `type`、`__class__`、`__mro__`、`__subclasses__` 等）。

**本项目 `tools.py` 的 `_ALLOWED_IMPORTS` 白名单虽在 AST 层面检查 import 语句，但 `__builtins__` 白名单不完整**——`open` 在内但 `__import__` 在 `_safe_import` 中仍被放行，且 `compile()` 源码内可以通过其他途径获取 `__import__`。这是一个实际风险面。

#### 论断 B：双时间轴事实（bi-temporal facts）是已验证的成熟范式

**查证结果：✅ 正确**。Zep 和 Graphiti 均采用 `valid_at` / `invalid_at` 双时间轴：

- [Zep 时间知识库架构](https://deepwiki.com/getzep/zep/2.1-temporal-knowledge-graph)：显式记录 `valid_at` / `invalid_at` 来管理事实有效性。
- [Zep 血统追踪博客](https://blog.getzep.com/how-zep-tracks-provenance-in-agent-memory/)：事实层用双时间轴 + 证据下钻。
- [nexus Issue #1183](https://github.com/nexi-lab/nexus/issues/1183)：`feat: Add bi-temporal fields (valid_at/invalid_at) to MemoryModel`

本项目的实现与 Zep 模式一致，是行业最佳实践。

#### 论断 C：0.8B 模型能力是实际天花板

**查证结果：✅ 确认**。

- [delimitter/qwen2.5-0.8b-synoema-tools-v2](https://huggingface.co/delimitter/qwen2.5-0.8b-synoema-tools-v2)：针对工具调用专门 fine-tune 的 0.8B 模型，C4 评测 96.4%，但工具调用成功率远低于大模型。
- [Qwen3-Zero-Coder-Reasoning-0.8B](https://huggingface.co/DavidAU/Qwen3-Zero-Coder-Reasoning-0.8B)：0.8B 代码推理模型，仍需专门 distillation。

README 声称的 0.8B 对话准确性（3/5 · 5/5 · 4/5）在合理范围内。核心瓶颈不是 harness，是小模型本身的推理能力。

#### 论断 D：`os._exit(1)` 硬杀进程跳过清理

**WorkBuddy 审查 #12** 指出。查证 Python 文档：

`os._exit()` 不执行 `atexit` 钩子、不 flush I/O 缓冲、不跑 `try/finally` 清理。与 `sys.exit()` 不同，`os._exit()` 直接调用 C 层 `_exit()`，跳过所有 Python 层清理。

本项目的 `ui_server.py` 用 `os._exit(1)` 让 launchd 重启，确实会丢失未提交的数据库事务。应改用 `sys.exit()` 或先 `commit()` 再退。

### 3.3 独特发现：前两份审查未指出的问题

#### 发现 1：MetaObserver 自我观察结果恒误报（🔴 正确性）

`test_meta_observer_healthy` 写入 5 条 >20 字的正常输出，但 MetaObserver 报告"空洞率 1.0"——100% 被判定为空洞，自我观察完全失效。

**已排查路径：**

- `land_thought` 写入列名 `source_output` 正确（`graph_db.py:611`），与 MetaObserver 查询列名一致
- `add_node` 创建的节点存在 `source_output` 列（`graph_db.py:176`，默认空字符串）
- 参数映射正确：`output` 参数 → `source_output` 列

**疑似根因：** `land_thought` 方法（`graph_db.py:604-633`）**未显式调用 `commit()`**。虽然同一连接内未提交变更对当前连接可见，但 `_LockedConn` 与 `DB_LOCK` 交互可能导致提交时机不确定。这是前两份审查均未发现的问题，且直接导致 `test_meta_observer_healthy` 失败和整个自我观察器官可能失效。

#### 发现 2：`test_meta_observer_detects_spinning` 的复读检测依赖相邻行

`meta.py:51-52`：

```python
for a, b in zip(outs, outs[1:]):
    if a and a == b:
        repeats += 1
```

只有**相邻两行**完全相同（前 30 字）才算复读。如果复读是每隔一行出现一次，检测会漏掉。这不是 bug，但检测灵敏度有限。

#### 发现 3：`test_scale_10k` 触发 numpy 除零警告

`memory_index.py` 在 10k 事实的 `test_scale_10k` 测试中产生 3 条 numpy 警告。虽然不影响功能，但提示向量索引在边界情况下（全零向量）需要防护。

#### 发现 4：`ui_server.py` 重复实现了与 `brain._idle()` 相同的闲时逻辑

`ui_server.py:119` 的 `breathe_loop` 在 `get_next_focus()` 返回 None 时直接调用 `brain._idle()`，但主循环体 `_breathe_body` 和 `_breathe_once_safe` 两条路径有轻微差异——前者在 `idle` 后 sleep 15s，后者不 sleep。如果主权管家增聘了多个工人，每个工人都走 `_breathe_once_safe`（不 sleep），会形成高频空转，浪费资源。

#### 发现 5：README 的 0.8B 评测数据缺少可复现性说明

README 声称"0.8B 对话 3/5 · 5/5 · 4/5"，但未说明评测条件（模型版本、prompt 模板、评测数据集、评分标准）。这使得该数据无法被第三方复现验证。

### 3.4 架构层面分析

#### 3.4.1 耦合度

`brain.py`（945 行）是项目的核心调度器，但承载了过多职责：

- 呼吸循环控制
- prompt 模板装配（4 个分支，各 20-50 行模板字符串）
- Zoom Out/In 解析与执行
- 闲时治理（`_idle()`，120+ 行）
- 里比多状态机
- 造机规划
- 领土生长

理想拆分：`brain.py` 只保留呼吸循环 + 调度，prompt 模板独立为 `prompts.py`，闲时治理拆为 `idle_policy.py`。

#### 3.4.2 两个入口点重复初始化

`main.py` 和 `ui_server.py` 都有相同的装配序列：

```
GraphDB → ensure_schema → create_backend → Brain → DMN
```

应抽取为统一的 bootstrap 函数（如 `focus.bootstrap.create_app()`）。

#### 3.4.3 facts 表无淘汰

双时间轴只失效不删除。长期运行后 `WHERE invalid_at IS NULL` 的扫描开销随历史事实线性增长。`memory_index.py` 的 `ensure()` 也是全表扫描。建议：

- 加 `vacuum` 定期归档历史事实
- 或引入 `facts_snapshot` 表（快照式归档）

#### 3.4.4 进化"改了不生效"的隐蔽 bug

`evolution.py` 用 `setattr(config, param, v)` 改写模块全局变量，但 `dmn.py` 中的某些值（如 `DREAM_EVERY_SEC`）可能在类定义时被硬编码为类属性。即使全局变量被更新，类属性的值不会自动刷新。前一份 WorkBuddy 审查已指出此问题。

#### 3.4.5 中文耦合

所有 prompt 模板、seed skills、测试数据都是中文。国际化几乎不可能，但作为个人实验项目可以接受。

### 3.5 安全层面分析（综合两份审查）

**P0（已确认高危）：**

1. **Python 工具沙箱可绕过** — 已知 CVE 验证此技术可行
2. **网学内容直接写 facts** — 无求证、无授信、无隔离审核
3. **端口无认证** — 本地低危，但端口暴露即远程可操控

**P1（确认中危）：**

4. **`os._exit(1)` 硬杀跳过清理** — Python 文档确认
5. **`ui_server` 模块顶层副作用** — 无法在不启动服务时 import
6. **单 SQLite 连接多线程** — 全局 RLock 串行化可能成为瓶颈

**P2（确认低危）：**

7. **facts 表全表扫描** — 规模增长后性能退化
8. **日志无轮转** — 长期运行撑爆磁盘
9. **依赖无上界** — 未锁定版本

## 四、"是否达到了一个可用的 Agent 的状态？"

### 4.1 能用的证据

- ✅ 186/189 测试通过（98.4%）
- ✅ 三种后端（dummy / MLX / OpenAI 兼容），dummy 模式无模型可跑通
- ✅ Web UI（:8765）可发话、看 Graph、看实时意识流
- ✅ 工具真实执行（ls/cat/python/bash/web_search/web_read）
- ✅ 记忆真实落盘并检索（facts + core_memory）
- ✅ Zoom Out 拆解 → Zoom In 执行 → 工具调用形成闭环
- ✅ 自我觉察（AST 扫描自身代码）
- ✅ 自我进化（参数空间 + 门禁）

### 4.2 不能"实用"的瓶颈

| 瓶颈 | 严重程度 | 说明 |
|---|---|---|
| 模型质量天花板 | 致命 | 0.8B 的推理质量决定 Agent 实质能力。对话准确性波动大，长任务成功率约 ⅔ |
| 无端到端验证 | 严重 | 所有测试是单元测试 + 合成用例，没有"用户提需求→Agent 交付成果"的真实场景 |
| 启动门槛高 | 中等 | 需 LM Studio 起 0.8B 服务或配置 sensenova API key |
| 安全性未达生产标准 | 严重 | Python 沙箱可绕过、网学内容直接写库 |
| MetaObserver 可能失效 | 中等 | 列映射不匹配导致自我观察可能永远误报"空洞" |

### 4.3 结论

**是一个可运行的实验性 Agent，但不是实用工具。**

- 作为**技术验证 / 研究原型**：**充分**。架构设计精良，20+ 模块全部有实际实现，小模型工程学做得扎实，是同类开源项目中设计最完整的一个。
- 作为**日常可用工具**：**不足**。瓶颈在模型质量和缺乏端到端验证，而非 harness 本身。
